Recommendation · greenfield replacement

Delete the engine.
Keep the discipline.

ForgeDock should not port its Claude-era engine to Pi. It should replace that engine with a small, typed workflow controller, use Pi as an embedded agent runtime, and expose a ForgeDock-owned CLI and TUI.

Pi is the execution kernel—not the workflow authority, state store, product identity, or durable memory. GitHub holds institutional memory. ForgeDock code owns transitions and side effects. Models do bounded reasoning and implementation work. This preserves the valuable behavior without preserving the accidental machinery.

Product contract

What survives the rewrite

The rewrite is allowed to destroy internal compatibility. It is not allowed to weaken externally observable safety.

01

Prove before coding

Every issue is investigated. The valid outcomes are confirmed, invalid, or decompose.

02

Freeze the job

A versioned Build Packet fixes scope, acceptance criteria, relevant history, plan, risks, and verification.

03

Verify with evidence

Tests, static checks, build commands, and acceptance checks are controller-recorded evidence—not model assurances.

04

Review independently

A reviewer starts in a fresh session with intent, packet, evidence, and diff; never the builder conversation.

05

Anchor to a SHA

Review approval is valid only for the exact reviewed commit. A changed head invalidates the verdict.

06

Recover from GitHub

GitHub is durable truth. Local databases and Pi sessions accelerate execution but cannot be the only record.

Determinism belongs at the boundary. ForgeDock controls phase selection, permissions, validation, retries, state transitions, merge eligibility, and closure. A model may propose; it may not silently govern.

interface AgentRuntime {
  capabilities(): Promise<RuntimeCapabilities>;
  run(task: AgentTask, signal: AbortSignal): AsyncIterable<AgentEvent>;
  resume(ref: EphemeralSessionRef, input: ResumeInput): AsyncIterable<AgentEvent>;
  close(ref: EphemeralSessionRef): Promise<void>;
}

type AgentTask = {
  role: "investigator" | "packet-author" | "builder" | "reviewer" | "remediator";
  objective: string;
  context: readonly DurableArtifact[];
  workspace: WorkspaceGrant;
  tools: readonly ToolGrant[];
  outputSchema: JsonSchema;
  modelPolicy: CapabilityPolicy; // no provider name required
};

Durable artifacts store role, result, and optional model provenance for audit. They never require a Pi session ID to remain usable.

Public surface

Three workflows, a few utilities

Users should express intent. They should not have to know internal stage names or select a recovery command for every failure mode.

core

forgedock work-on <issue>

Take one issue from intent through investigation, build, verification, PR, independent review, and configured completion.

core

forgedock review-pr <pr>

Run a fresh, SHA-anchored review against original intent; optionally enter controller-governed remediation.

core

forgedock orchestrate <set>

Schedule many work-on runs with dependencies, worktree isolation, conflict claims, leases, and bounded concurrency.

forgedock                         # open the branded interactive TUI

forgedock review-pr 167           # independent review at current SHA

Important consolidation: status, resume, and stale-run recovery are views/actions on one run model. They are not prompt-heavy commands with independent behavior.

Interactive work and review tools may place the typed controller in a native session-scoped background task so the supervisor remains responsive. Task logs and JSON records are operational only; GitHub artifacts remain semantic truth. Orchestration children stay synchronously owned, and cancellation or terminal shutdown kills the controller's complete process tree.

Controller responsibilities

  • Resolve repository state and permissions
  • Create worktree and enforce role grants
  • Select the next state from validated output
  • Run deterministic verification commands
  • Create/update issue, branch, and PR artifacts
  • Check SHA freshness and merge eligibility
  • Persist every committed transition

Agent responsibilities

  • Investigate claims against code and history
  • Produce schema-valid artifacts
  • Plan changes within frozen scope
  • Edit and test only inside the granted workspace
  • Explain evidence, decisions, and residual risk
  • Remediate only accepted blocking findings

Investigation branches are first-class

confirmedCreate the Build Packet and continue. Confidence/risk can determine whether preparation uses one or multiple fresh agents.
invalidPost evidence and a proposed terminal outcome. The controller applies configured closure policy; no builder is started.
decomposeCreate an explicit decomposition proposal and child intents. The parent reaches a durable decomposed outcome; children become ordinary work items.
No monolithic agent session. Investigation, build, and review are separate tasks. Session continuity may be used inside a role for recovery, but never as the workflow’s source of truth.
Workflow 2

review-pr: independent and commit-specific

The current many-agent review machinery should become a small review protocol with risk-based specialist routing.

INPUT

Clean review packet

Original issue intent, investigation, Build Packet, PR diff, verification evidence, repository policy, and current head SHA.

PROCESS

Fresh role sessions

One baseline reviewer is mandatory. Security, data, API, frontend, infrastructure, or other specialists are selected from changed surfaces and risk.

OUTPUT

One typed verdict

Every finding includes severity, confidence, evidence, location, intent relevance, remediation, and blocking status.

Deterministic policy, not reviewer vibes

ConditionController response
No blocking findings; required checks pass; SHA unchangedApprove. Merge only if repository policy permits auto-merge.
Actionable in-scope blocking findingEnter remediation with only accepted findings; re-run verification; review the new SHA in fresh context.
Head SHA changed during reviewInvalidate all outstanding verdicts and restart review at the new head.
Finding is speculative, out of scope, or lacks evidenceRecord as non-blocking or reject it; do not expand the build silently.
Retry/remediation budget exhaustedStop as blocked with a human-readable handoff. Never merge optimistically.
Recommended review roles

Always: baseline correctness/intent reviewer plus deterministic repository checks.

Conditional: security/auth, persistence/migrations, API compatibility, concurrency, frontend/accessibility, infrastructure/CI, or domain-specific review. Selection is code/config, based on changed paths, diff semantics, Build Packet risks, and repository policy.

Removed: a fixed fan-out to every specialist and a large prose orchestrator that asks a model to decide what review means.

Independence boundary
The reviewer may use the same model family if that is the configured option, but receives a new Pi session, no builder transcript, no builder scratchpad, and no uncommitted workspace state. For high-risk changes, policy may require a different provider/model class as an additional independence measure.
Workflow 3

orchestrate: schedule work, do not invent a second pipeline

An orchestration worker runs the same work-on state machine. Orchestration adds coordination only.

Keep

  • Explicit dependency DAG and cycle detection
  • One isolated worktree per active issue
  • Bounded concurrency and resource budgets
  • Predicted and observed path/component claims
  • Lease, heartbeat, stale-worker recovery
  • PR head freshness and merge sequencing
  • Restart/reconciliation from durable artifacts

Do not carry forward

  • Recursive opportunistic cascades
  • Near-miss/backlog mining inside execution
  • Complex value/cost scoring as a model task
  • Model-authoritative batching or completion sweeps
  • Background shell dispatch as workflow control
  • A second set of build/review semantics
  • Agents writing authoritative scheduling state

Minimal scheduler

ready = issues
  .filter(dependenciesSatisfied)
  .filter(notTerminal)
  .filter(noActiveLease)
  .filter(claimsCompatible)
  .sort(byConfiguredPriorityThenAge);

while (capacity.available && ready.length) {
  controller.startWorkOn(ready.shift(), isolatedWorktree());
}

The selected model interprets a natural-language issue query and proposes evidence-backed dependencies, priorities, and coarse path/component claims. Typed code validates the graph, rejects cycles or unselected dependencies, and materializes bounded topological batches. Claims become precise after the Build Packet (expected paths). Actual changed paths are checked before publish and before merge. A conflict blocks or serializes work; a model does not “reason away” the collision.

Decomposition is explicit, not a cascade. Child issues can be offered for enqueueing, but the scheduler does not recursively discover and launch unrelated work unless a user-configured query includes it.
Durable memory

Six artifacts replace annotation sprawl

Each artifact is schema-versioned JSON with a human-readable Markdown projection on the issue or PR. The JSON is authoritative for machines; the Markdown remains useful to people.

01

Intent

Problem, desired outcome, constraints, source, acceptance hints, links, and dependency declarations.

02

Investigation

Outcome, confidence, evidence, root cause, affected surfaces, risk, and decomposition proposal.

03

Build Packet

Frozen scope, criteria, context/history, implementation plan, verification plan, risks, and out-of-scope items.

04

Build Result

Branch/SHA, changes, criteria evidence, commands and results, artifacts, decisions, and residual risks.

05

Review Verdict

Reviewed SHA, reviewer roles, checks, structured findings, disposition, and freshness metadata.

06

Outcome

Merged, invalid, decomposed, blocked, or abandoned; final references, reason, and completion timestamp.

Operational state is separate

Run ID, state, attempt, lease owner, lease expiry, heartbeat, workspace, target branch, and ephemeral session references belong to a run record—not semantic artifacts. GitHub receives committed transitions and recovery metadata. SQLite is a rebuildable local index/cache. Pi session files are diagnostic execution records only.

GitHub must be enough to…

  • Understand why work was attempted
  • See what was proved and planned
  • Audit what changed and how it was verified
  • Know exactly which SHA was reviewed
  • Determine the terminal outcome

Local state may improve…

  • Fast status queries and TUI rendering
  • Streaming event history and cost tracking
  • In-flight process recovery
  • Workspace bookkeeping
  • Session continuation within one role

Compatibility: keep the existing protocol parser as a read-only migration layer. New runs emit v2 artifacts. Legacy sentinels/labels can be projected during a bounded transition period, then removed.

Product experience

Pi underneath; ForgeDock everywhere the user looks

A theme alone is not a product shell. The long-term TUI should expose workflow concepts rather than a generic chat transcript.

Run timeline

Current state, completed barriers, attempts, elapsed time, active model, tool activity, and the next controller action.

Review desk

SHA, checks, findings grouped by severity, accepted/rejected rationale, diff locations, remediation status, and merge control.

Orchestration board

Dependency graph, ready/running/blocked lanes, leases, conflict claims, worktrees, budget, and concurrency.

Model profiles

Select providers/models by role or capability. Show context limits, tool/image support, reasoning levels, cost, and availability.

Human checkpoints

Edit/approve the Build Packet, override rejected findings, stop runs, approve merge, and see consequences before acting.

Developer cockpit

Attach to a role session, open the worktree/editor, inspect commands, rerun a gate, export diagnostics, and resume safely.

Anti-lock-in design

Provider neutrality needs architectural enforcement

Model-provider neutral

  • No provider names in workflow transitions
  • Role selection by capabilities and policy
  • Built-in, proxy, OAuth, gateway, and local models supported through Pi
  • Cross-provider handoff uses ForgeDock artifacts, not hidden chat state
  • Per-role provider/model configuration is optional, not required

Runtime neutral

  • All Pi use stays in one adapter package
  • Workflow tests run against an in-memory fake runtime
  • ForgeDock owns task/event/output schemas
  • No Pi session format in durable contracts
  • A second runtime can pass the same conformance suite later

Pi is still a dependency. It is a good dependency here because it is MIT-licensed, SDK-embeddable, and already supports multiple API families and custom providers. The runtime port prevents that sensible choice from becoming the next irreversible product boundary.

GitHub is an intentional product dependency. It remains the first durable host because the product’s core promise is institutional memory in issues and PRs. Put it behind a ForgeHost port so GitLab or another host is possible later, but do not dilute the first implementation with premature multi-host parity.

Safe delivery

“Scrap the engine” should not mean “forget what production taught us.” Preserve behavior through fixtures and acceptance tests, not copied architecture.

Definition of done

The rewrite succeeds only if these remain true

Workflow behavior

  • Invalid issues stop before coding with evidence
  • Decomposed parents produce linked, independently runnable children
  • Builders cannot broaden frozen scope silently
  • Verification records executable results
  • Review starts without builder conversation context
  • Any changed SHA invalidates prior review
  • Blocking findings force fix, verification, and re-review

Portability and recovery

  • The same workflow runs on at least two providers
  • A local/custom provider can be configured without workflow code changes
  • The controller test suite passes with a fake runtime and no Pi
  • A killed run reconciles without guessing from chat history
  • A second machine can understand completed work from GitHub alone
  • Two conflicting issues are serialized or blocked deterministically
  • No role can exceed its side-effect grant

Final recommendation: approve a greenfield ForgeDock core, delete rather than port the current engine, embed Pi behind a ForgeDock runtime boundary, and delay deep TUI customization until the new workflow contract is executable. The moat is not the old engine or a particular model. It is reliable, recoverable software delivery with durable institutional memory.
